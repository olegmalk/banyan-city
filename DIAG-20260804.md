## Why the worker is still down (deliberate, please read before restarting)

Restarting right now would do exactly one thing: re-run the task that just took
the machine down. Two reasons I stopped instead:

**1. The only outstanding queue item is the fatal one.** `faceneg-b01-1785819600`
already shows `DONE` in the heartbeat. `bench-animegen-b01-1785827400` is the sole
remaining task for this worker. There is no other work a restart would pick up.

**2. The retry guard cannot stop this loop — it is blind to BSODs.**
`finished_tasks()` counts `FAIL task=<id>` lines out of heartbeat.txt, and
`MAX_ATTEMPTS = 2`. Grepping heartbeat.txt for this task returns **only**:

```
07:12:18Z STARTED task=bench-animegen-b01-1785827400 beats=1 on cuda
```

No `FAIL` line — because writing one requires the worker to survive the failure,
and this failure kills the host. **Recorded attempt count for this task is 0.**
A restarted worker treats it as brand new. Every future BSOD erases the evidence
that would eventually stop the retries, so this is a crash loop the existing guard
is structurally unable to break. (The 2026-08-03 `anime-canary-b07` attempts *did*
accumulate FAIL lines precisely because those crashes killed only the child.)

This is a genuine gap in the guard, not just a fact about today: **any failure
mode that takes down the OS is invisible to the attempt counter.**

## The proposed fix may not be sufficient on this box — check this first

farm-queue.yaml:46-49 diagnoses the load path: `load_animegen` (wan_i2v.py:164-167)
loads both A14B transformers in bf16 *then* casts to fp8, peaking ~64 GiB host RAM,
with cpu-offload keeping **~38 GiB resident afterwards**. The proposed fix — load
`hi`, cast, then load `lo`, cast — takes the *peak* from ~64 to ~32 GiB.

Against this machine's actual numbers:

- **Physical RAM: 31.4 GB usable** (2 x 16 GB SK Hynix 5600).
- Pagefile: 58 GB, system-managed. Commit limit 89.4 GB.

So: peak ~64 GiB against 31.4 GB physical = ~33 GB of hard paging, which matches
the "HOST RAM" diagnosis. But note that **the fix only addresses the peak. The
~38 GiB steady-state offload residency is untouched by load order, and 38 GiB
still exceeds 31.4 GB of physical RAM.** The model would page continuously through
every offload step of all 25 steps, with an expert swap per step.

I have not proven that causes the access violation, but the honest read is that
the one-line load-order fix is necessary and probably **not sufficient** here, and
AnimeGen at 14B x 2 may simply not fit a 32 GB host regardless of load order.
Worth deciding before spending another sample on it. Cheapest disambiguation:
instrument peak working set during load, or test on a 64 GB host.

VAE tiling / offload status in the failing stage, since it was asked: `offload:
true` was set in the task and `enable_model_cpu_offload()` is on the AnimeGen path
(wan_i2v.py:187); wan_i2v.py:191 prints "AnimeGen: fp8 layerwise casting + cpu
offload + VAE tiling". **Neither was reachable as a cause this time** — the crash
was at 11:13:43, ~56s in, during model load, well before VAE encode. The prior
VAE `_encode` OOM (fixed in fb1e43e) is a *different* failure and did not recur.
